# ADR 0006: 通知收件箱（铃铛下拉 6 条 + 列表页删除）

## 状态

已接受（2026-10-29）。同步修订 `REQUIREMENTS.md` 4.13 节、`docs/api/API.md`、`frontend/src/router/ROUTES.md`。

## 背景

`messages` 表此前只有**铃铛下拉**一个消费面，且下拉内联翻页（`加载更多`，一次 20 条）。由此暴露三个问题：

1. **下拉不是收件箱**：下拉展开宽度有限，却要承担"逐条读通知 / 清理旧通知"的动作。没有删除能力时，通知只能靠"标记已读"消化——旧通知永远堆在列表最前面。
2. **点击语义含糊**：下拉里点击一条通知，既标记已读、又按 `link` 跳转，条目还在原位变灰。跳转来自通知里一个可能失效的 `link`（worker 写入的 `/settings/subjects` 与实际路由 `/subjects` 已不一致），用户会落到 404 式空页。
3. **孩子端无入口**：铃铛是共用的，但孩子端没有通知列表页，清理自己那部分通知无路径。

## 决策

### 1. 新增通知列表页（家长 + 孩子共用同一页面组件）

- 路由：家长 `/messages`、孩子 `/kid/messages`，两者挂**同一个** `MessageListPage.vue`。
- 形态参考试卷列表：`bg-card` 卡片壳 + `Table` + 卡片内「上一页 / 下一页」按钮。
- **不做**过滤（未读/已读只由圆点表达）、**不做**详情页（通知本身只有一行文字，没有详情可看）。
- 分页沿用 **keyset 游标 + 游标栈**（同 ADR 0003）：keyset 无法反向直达，"上一页"靠栈回退。

### 2. 铃铛下拉降级为"一瞥"

- 只取**最新 6 条**（`limit=6`），去掉内联 `加载更多`。
- `has_more` 为真时，底部给「全部通知」按钮，跳到当前端的列表页（`allTo` prop：家长 `/messages`、孩子 `/kid/messages`）。
- 点击一条通知**仅标记已读**：条目留在原位、圆点由实色转浅灰、**不跳转**（`@click.stop`，面板不因该点击关闭，用户能看见圆点变化）。

### 3. 新增 `DELETE /api/messages/:id`（物理删除）

- **物理删除而非软删**：通知除已读/未读外无业务状态，墓碑只会让表膨胀，并使 keyset 游标语义变浑浊。
- **收件人边界双重校验**：service 层校验 `audience`/`kid_id` 配对，repository 的 `WHERE` 再带一遍
  （`WHERE id = ? AND audience = ? [AND kid_id = ?]`）。任一侧失效都不会误删他人的通知。
- 边界取自 **token 受众**（`audience` / `kid_id` 从 JWT 上下文取），**绝不取自请求体**。
- 语义：命中 0 行 → `domain.ErrNotFound` → **404**（不区分"不存在"与"无权限"，避免探测）；非法 id → 400；成功 → `ok(c, nil)`（与 `DELETE /api/subjects/:id` 等保持一致，不新增 DTO）。

### 4. 已读/深链语义重新划界

- 下拉：点击 = 标记已读，不跳转。
- 列表页：标题带 `link` 时渲染为 `RouterLink`，点击**跳转 + 标记已读**；无 `link` 时为按钮，仅标记已读。
  `link` 的深链语义因此保留在能承载它的页面上（REQUIREMENTS 4.13）。

## 理由

1. **职责分离**：下拉负责"现在有什么新消息"（一瞥），列表页负责"处理历史通知"（翻页/删除）。两者用不同的控件承载不同的信息密度。
2. **6 条是"一瞥"的自然上限**：一屏能读完的量；再多就需要滚动，而滚动中的下拉正是可用性最差的形态。
3. **删除是通知系统不可缺的能力**：否则唯一的消化方式只有"标记已读"，旧通知永远占位。
4. **物理删除 + 双重边界校验**：通知是派生数据（系统写入的提醒），不是业务台账；删除后无需留痕，但**边界必须严**——越权删除不可接受，故在 service 与 SQL 两层各卡一次。
5. **深链只在列表页生效**：下拉点击后原地跳转会让用户失去"还有几条没读"的上下文，且失效 `link` 会把用户带离页面；列表页有明确的位置感，点了就知道自己在哪。

## 影响

- **后端**：`domain.MessageRepository` 新增 `Delete(ctx, id, audience, kidID) error`；`MessageRepoSQLite.Delete` 走写池；`MessageService.Delete`；`MessageHandler.Delete` 注册 `DELETE /api/messages/:id`。
- **前端**：新增 `pages/MessageListPage.vue`；`MessageBell.vue` 改为 6 条 + 「全部通知」+ 点击仅标记已读（新增 `allTo` prop）；`Layout.vue` 按端传 `all-to`；路由新增 `messages` / `kid-messages`；`messageApi.remove(id)`。
- **契约**：`docs/api/API.md` 两端共用接口 21 → 22，合计 60 → 61。
- **已知遗留**（本次未改，另行处理）：worker 写入的深链 `/settings/subjects` 与实际前端路由 `/subjects` 不一致——列表页的深链跳转仍会落到不存在的路径。
- **回归防护**：铃铛用例改写为"6 条 / 点击仅标记已读 / 全部通知跳转"；新增列表页用例（渲染、分页游标、删除确认、空态、错误态重试、标记已读、深链跳转、全部已读、孩子端共用）。
